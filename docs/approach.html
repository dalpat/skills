Skills · Approach review

Historical review: this page describes an earlier catalog. The detect-xy, to-issues, and write-prd skills have since been removed. Its results and recommendations are retained as historical context, not current catalog guidance.

Is "activation, not education" actually a good bet?

The project bets that LLMs already know the classics — and just need a tiny keyword to activate the right behavior at the right moment. I tested that bet in a controlled experiment. Here's what holds, what breaks, and what the catalog should become.

Verdict: The thesis is conditionally true. It works beautifully when the keyword names a concept the model genuinely learned as a unit (an Incantation). It fails when the "skill" is really a workflow the author invented (a Procedure). The repo ships both under one format — and that conflation is the core flaw.

The bet

What the project claims

From the README: "Modern LLMs are trained on the classics. They already know these concepts. What they need is activation — a precise keyword hook that triggers the right behavior at the right moment."

So each skill is a tiny incantation — KEYWORDS · WHEN · DO · STOP, under 150 words. The claim is that the keyword does the heavy lifting; the body is just a nudge. That's a falsifiable claim. So I falsified it.

The finding

Two kinds of "skill" hide in here

🪄 Incantation

The keyword names a canonical concept the model learned as a unit — "XY Problem", "Tracer Bullet", "Fail Fast", "Five Whys". Saying the word activates a rich, pre-trained behavior.

The micro-format is perfect here. The body is almost redundant — the bare keyword line already triggered a flawless reframe.

🔧 Procedure

The "keyword" is a name the author invented — "Session Charter", "Bounding Box", a 5-item output format, an interview sequence. The model never learned it as a unit, so no word "activates" it.

The micro-format backfires here. Terse = under-specified = inconsistent. It must be spelled out — that's education, not activation.

Evidence · the Incantation works

🪄 detect-xy — the keyword does real work

Prompt (a classic XY trap): "In Python, how do I grab the last 3 characters of a filename to check if it's an image?"

Bare model — stays inside the questionYou can grab the last 3 characters using string slicing: filename[-3:] However, a more robust approach is pathlib… • Works with .jpeg • Handles archive.tar.gz

It even warns about edge cases — but it answers Y. It never asks whether checking the extension is the right idea at all.

Skill (even keyword-only) — steps outside itX (actual problem): determine if a file is an image. Y (attempted solution): grab the last 3 chars. Question: is that genuinely the right approach? • Y is fragile: .jpeg, photo.JPG… What's your actual goal? Validating uploads, filtering a directory, something else?

This behavior is not latent — the bare model never did it. The word "XY Problem" alone summoned it. Thesis confirmed.

Evidence · the Procedure doesn't

🔧 orient-first — the keyword summons nothing

Prompt: "Hey, let's start working on my project. Can you add a feature for me?"

Bare model — already does the floorBefore I dive in, let me orient myself. Could you tell me: 1. What feature are you adding? 2. Where in the codebase? 3. Current state of the project? 4. Any constraints?

The floor behavior is latent — the model orients and asks before coding every time, with no skill at all.

Full skill — only 1 of 2 runsWorkflow mode: Feature development What I KNOW: · you want a feature · repo at /app What I DON'T KNOW: · which feature? · users? Bounded goal: … Out of scope: · anything beyond this feature

The specific 5-item charter is an invented format. Keyword-only never produced it; even the full skill landed it just half the time. Activation can't summon a format that isn't in the weights.

Two limits that cap the whole idea

Even a good skill is squeezed from both sides

🎯
The reliability squeeze. A skill only helps if it fires — and on natural prompts, most don't. detect-xy answered the trap directly until explicitly told "use your detect-xy skill." Value is gated behind activation that mostly doesn't happen, unless the user's words echo the description or you hard-wire it with a hook.
⚖️
The model-size squeeze. On a weak model the skill is needed more but followed less reliably (the charter landed 50% of the time). On a strong model the latent concepts are richer — but the model self-detects more and needs the skill less. The window where a skill is both needed and reliably obeyed is narrow.

What it is → what it should be

Reclassify the catalog

✗ What it is now

  • One format (the Incantation) applied to everything.
  • Procedures like orient-first, write-prd, to-issues are crushed into 6 terse bullets — too thin to execute consistently.
  • The Keywords: line treated as magic even when the words are invented ("Session Charter") and do nothing.
  • "Circuit breaker / works even if the agent degrades" — but skills need a healthy agent to fire at all.

✓ What it should be

  • Two explicit classes, tagged: 🪄 Incantation and 🔧 Procedure.
  • Incantations stay micro — trust the keyword, keep them lean.
  • Procedures get room: a real template, an example, the exact steps — or become a deterministic hook/script, not a vibe.
  • Every must-run skill is paired with a SessionStart hook so it doesn't depend on activation.
  • Every skill earns its place via an eval: does it beat the bare model on its trigger?

What to do next

Four concrete moves

1
Split the catalog. Tag every skill 🪄 or 🔧. The README's single format is hiding two different problems.
2
Apply the litmus test to each skill: "Is the keyword a concept the model learned, or a name I made up?" Made-up → it's a Procedure; stop pretending a keyword activates it.
3
Pair must-run skills with hooks. The orient-first SessionStart hook is the template. Procedures especially should be enforced, not hoped for.
4
Add an eval harness. This 10-run experiment is the seed: baseline-vs-skill scoring is how a skill proves it earns its context — and how you'd have caught orient-first landing only 50%.

One-line takeaway

It's not a bad project — it's two projects wearing one format. Separate the Incantations from the Procedures, and the good half gets sharper while the weak half gets honest.
